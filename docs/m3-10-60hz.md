# M3-10 60 Hz at 1080p at the gated edge

**Status:** landed 2026-11-01. 1920×1080, 128³ chunks, the 256-chunk scene, 1200
recorded frames at a pinned pose. The **RTX 4060 clears 60 Hz by a wide
margin** (average 192–202 fps, 1% low 104–113). The **Radeon iGPU clears 60 Hz
on average (70–75 fps) but its 1% low sits on the line at 57–61 fps**: the
average frame is 13–14 ms with a 99th percentile of 15.9–17.3 ms against the
16.6 ms budget. That is the open condition carried to M3-13.

## Acceptance

| Requirement | Measured |
|---|---|
| 1080p | 1920×1080 drawable on both GPUs |
| Gated edge | 128³ chunks (`--features chunk128`), 256-chunk ring, 95 chunks / 845,446 quads / 35.5 MiB drawn at the gate pose |
| Recorded average | RTX 4060 **192.0–202.5 fps**, Radeon iGPU **70.2–75.1 fps** |
| Recorded 1% low | RTX 4060 **104.3–113.0 fps**, Radeon iGPU **56.6–61.2 fps** |

## Method

`VOXEL_FRAMETIME=path.json` makes the viewer record the interval between two
`Queue::present` calls for 1200 frames once the whole ring is resident, then
write a JSON report and exit 0. The interval is what a player sees: draw,
submit, present and the swap chain. M3-06's CPU submit and GPU pass numbers are
recorded alongside it so a miss can be attributed.

```sh
cargo build --release -p voxel-viewer --features chunk128
VOXEL_FRAMETIME=target/m3-10-4060.json \
VOXEL_FRAMETIME_EYE=14,6,20 \
VOXEL_FRAMETIME_TARGET=2,1,2 \
  ./target/release/voxel-viewer
```

The pose is pinned because the interactive start camera can be rotated by stale
pointer events while the window settles; without a pin, two runs do not measure
the same view (a 81-vs-95-chunk difference was observed). `(14, 6, 20) → (2, 1,
2)` is the M3-08 screenshot pose, so the numbers and
[`images/m3-08-stress-scene.png`](images/m3-08-stress-scene.png) describe the
same frame.

### What "1% low" means here

The recorder reports the frame-rate form of the slowest bucket: the average of
the **slowest 1% of frame intervals**, inverted (`n / Σt`). The 0.1% low uses the
slowest 0.1%, clamped to at least one frame. The statistical `frame_p99` is also
in the report but is a different thing — over 100 samples the p99 is the 99th
value, which excludes the worst frame; the 1% low includes it.

A 60 Hz gate needs the 99th percentile frame to fit 16.6 ms, i.e. a 1% low of at
least 60 fps. The 0.1% low is reported for context and is not gated.

## Measured

Release, 1920×1080, default seed, gate pose, 1200 frames, ring resident.

### 128³ — the gated edge

| | RTX 4060 (3 runs) | Radeon iGPU (8 runs) |
|---|---:|---:|
| Average | **192.0 / 201.0 / 202.5 fps** | **70.2–75.1 fps** |
| **1% low** | **104.3 / 113.0 / 105.2 fps** | **56.6–61.2 fps** |
| 0.1% low | 92.6–102.5 fps | 51.3–59.4 fps |
| Frame p50 | 4.42–4.88 ms | 12.98–14.37 ms |
| Frame p99 | 8.30–9.26 ms | 15.94–17.30 ms |
| Frame max | 9.88–11.89 ms | 17.18–18.30 ms |
| CPU submit p99 | 2.07–2.82 ms | 1.64–2.05 ms |
| GPU pass p99 | 0.69–1.78 ms | 8.22–8.47 ms |
| Drawn | 95 chunks, 845,446 quads, 35.5 MiB | same |

**Verdict.** The 4060 is present-bound, not geometry-bound: a 0.4–1.8 ms render
pass inside a 4.4–4.9 ms frame, with the 1% low 1.7× above the bar. The iGPU is
**draw-bound** (8.2–8.5 ms of a 13–14 ms frame) and lands 1–2 fps short of the
1% low bar: its 99th percentile frame is 15.9–17.3 ms against 16.6 ms. It passes
about half the runs and misses the others; the average has ~10–15 fps of margin,
the tail has none.

### 64³ — context, not the gate

| | RTX 4060 | Radeon iGPU |
|---|---:|---:|
| Average | 221.5 fps | 119.1 fps |
| 1% low | 127.9 fps | 87.0 fps |
| Frame p50 | 4.32 ms | 8.12 ms |
| GPU pass p99 | 0.15 ms | 3.33 ms |

At the baseline edge the iGPU clears 60 Hz with room. The gate is specifically
about 128³, where the mesh is ~4× the bytes and the pass triples.

## What was tried

**Front-to-back draw order** (early-z): implemented, measured, reverted. It did
not move the iGPU's pass (7.71–7.81 ms versus 7.70–8.30 ms unsorted) — the scene
is one heightfield layer with little overdraw — and it cost a per-frame sort, so
the M3-05 decision to keep map order stands.

The obvious levers are all out of this task's scope: fewer quads needs scene LOD
(M3.5), a cheaper vertex/fragment path needs the indirect work (M5), and the
~3 ms tail above the p50 is present-path time (the 4060 shows the same absolute
tail) rather than render-pass time.

## Tests

```bash
cargo test -p voxel-viewer --lib frametime
cargo test -p voxel-viewer --lib pose
```

- `frametime::tests` pin the 1% low (the slowest 1% bucket, including a single
  hitch), the 0.1% low bucket rounding, a steady 60 Hz run clearing the gate,
  and the JSON's context fields.
- `pose::tests` pin the pinned camera and the `x,y,z` parser.
- `stats::tests` pin the nearest-rank percentile the report uses.

## Limits

- **Uncapped, not vsync-paced.** WSLg's present is not throttled to 60 Hz, so the
  average is the machine's capability. On a real 60 Hz swap chain every frame
  below 16.6 ms would present at 16.6 ms and the 1% low would read 60; the gate
  measures headroom, not the paced result.
- **One pose, one seed, one scene.** The gate pose faces the forest/sand/rock
  mix; a view of the whole ring from above is cheaper, a close-up of dense
  canopy is dearer.
- **iGPU run-to-run spread is ±5%** (70.2–75.1 fps average), and the 1% low spans
  56.6–61.2. The pass/fail line is inside that spread.
- **The iGPU tail is not explained by the render pass.** Its pass p99 (8.2–8.5
  ms) is stable while the frame p99 moves 1.4 ms between runs; the extra tail is
  present/compositor time, and the 4060 shows the same ~3–4 ms gap above its p50.
- M3-11 (memory) and M3-13 (exit) carry the iGPU 1% low as an open condition.
